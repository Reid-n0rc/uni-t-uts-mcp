# Agent notes

Instructions for AI coding agents (Claude Code, Codex, etc.) working in this repo. `CLAUDE.md` points here.

## Project

MCP server (TypeScript, stdio) for UNI-T UTS series spectrum analyzers (UTS1000B/T, UTS3000B) over SCPI. Layout is modeled on [siglent-sds-mcp](https://github.com/MagnusJohansson/siglent-sds-mcp):

- `src/index.ts` – server entry, registers tool groups
- `src/registry.ts` – `InstrumentRegistry`: named instruments (default name `default`), the `UTS_INSTRUMENTS` parser, per-call selection through AsyncLocalStorage (`runWith`/`current`); `instruments` (the process-wide registry of `UtsConnection`s) lives there too, and `src/connection.ts` exports `connection`, a facade that forwards to the instrument selected for the running tool call, else the default one. Each connection has its own queue, hold-off and session lock, so different instruments never wait for each other (issue #67)
- `src/connection.ts` – SCPI connection (one per instrument): serialized queue, query timeouts, hold-off after a timed-out query, `*OPC?` command pacing, `msSinceQueryTimeout`, `expectSilence`
- `src/transports/` – the wire under `UtsConnection`. `transport.ts` defines the internal `Transport` interface (open/close/isOpen/onLost, `write` a line, `readLine`/`readBlock` with a timeout, `discardInput`) and its capability flags; `raw.ts` is raw SCPI over TCP (framing, CRLF, `#` block assembly, late-terminator swallowing); `vxi11.ts` is SCPI over the VXI-11 core channel on `Vxi11Client` (its capability flags are explicit documented constants, `VXI11_CAPABILITIES`, confirmed on the hardware in #75: no pacing, no hold-off, nothing dropped during a sweep; the instrument never answers a read that has nothing to deliver, so a timeout is the RPC deadline, the io_timeout sent is a fifth of the timeout, and there is no drain step: see the VXI-11 section of docs/verified-hardware.md before touching timeouts); `select.ts` parses `UTS_TRANSPORT` (raw|vxi11|auto, default auto; a port given without a transport choice means raw) and `UTS_VXI11_DEVICE`, validates the device name and probes the portmapper for `auto`. `UtsConnection.connect` takes `transport`/`vxi11Device` options and names a non-raw transport in its error messages. `src/acquisition.ts` picks the sweep wait by the `dropsInputDuringSweep` flag: raw stays silent and polls `*OPC?`, a transport that queues input writes `:INITiate:IMMediate` then does one blocking `*OPC?` read. Wire differences are expressed as capability flags (`syncsCommands`, `dropsInputDuringSweep`, `holdOffAfterTimeout`, `completeLargeBlocks`, read via `connection.capabilities`), never as transport-name checks in tools. A new transport implements `Transport` and passes `tests/transportContract.ts` by calling `runTransportContract` with its own factory and fake instrument
- `src/vxi11/` – dependency-free ONC RPC stack under the VXI-11 transport (#64): `xdr.ts` (bounds-checked XDR codec), `rpc.ts` (RPC v2 over TCP, record marking, xid matching, typed `Rpc*Error`s), `portmapper.ts` (`getPort`), `client.ts` (`Vxi11Client`: connect via portmapper or explicit port, chunked `write`, `read` looping until END, `readStb`, `clear`, `close`, `enableSrq`/`waitForSrq`/`disableSrq`; typed `Vxi11*Error`s with every VXI-11 error code named). `interrupt.ts` is the SRQ listener (`IntrServer`, peer-filtered, bounded; the instrument connects to it: untrusted input) and `localAddressFor`. Parses network input: keep every length capped and use `>>> 0` for the 0x80000000 record-marking bit (JS bitwise ops are signed)
- `tests/fakeRpcServer.ts` – in-process fake ONC RPC server + portmapper, reused by the VXI-11 fake instrument
- `tests/fakeVxi11Instrument.ts` – fake VXI-11 core-channel instrument (scriptable SCPI handler, simulated I/O timeouts, injected errors, dropped connections, a `firmware: true` mode that reproduces the real analyzer's silent read timeouts and one-slot output buffer, and a simulated sweep that queues commands and answers `*OPC?` only when the sweep ends)
- `src/sessionLock.ts`, `connection.runExclusive` – the per-connection FIFO exclusive-session lock; transport independent. Tools are serialized per instrument (see "Concurrency" below)
- `src/tools/screenshot.ts` – the `screenshot` tool: refuses unless the transport advertises `completeLargeBlocks` (VXI-11; raw truncates at 144,800 bytes, #42), selects PNG, reads `:DISPlay:DATA?`, restores the picture format in a `finally`
- `src/tools/*.ts` – one file per tool group, each exporting `register<Group>Tools(server)`; every tool is registered with `defineTool(server, name, description, shape, annotations, handler, options?)` from `src/tools/util.ts`
- `tests/fakeUts.ts` – the stateful fake UTS analyzer (#146): `UtsModel` (pure, injectable clock) behind `startFakeUts()` (raw TCP on 127.0.0.1). Models LF/CRLF framing, `*IDN?`/`*OPC?`, the error queue, silent clamping and -224 rejection, unsupported queries (no reply, ~2.15 s stall, late -113), the single-sweep window in which raw TCP drops lines (`transport: "vxi11"` queues them), trace data from `tests/fixtures/p2`, and the 144,800 byte screenshot cutoff. Every number carries a comment naming its docs/verified-hardware.md section (or is tagged ASSUMED); when you learn a new instrument behavior, record it in verified-hardware.md AND teach the fake. Measurement modes (#150): `:CONFigure:<meas>[:NDEFault]` presets span and parameters, `:CONFigure:SANalyzer` does not undo the span, no query reports the mode, mode-dependent queries stay silent, wrong-mode setters give -113, `:FETCh:`/`:READ:` results have the verified value counts and framing (READ: trailing space, no terminator over raw TCP). `model.loseNext(id, n)` silently drops the next n setters of a parameter, to exercise the restore-by-readback paths (#133). Measurement result numbers are constant noise-floor stand-ins, ASSUMED where verified-hardware.md has none
- `tests/e2e/stdio.test.ts` + `tests/e2e/e2eTable.ts` – spawns the BUILT server (`node build/index.js`, so run `npm run build` first; CI does) over stdio against the fake and calls every tool. **A new tool needs an entry in `E2E` and `ORDER` in `tests/e2e/e2eTable.ts` (steps with checks of the result and of the fake's state) or the "every registered tool has an entry" test fails**
- `tests/unit/`, `tests/integration/` – vitest; integration tests mock `src/connection.js`
- `docs/` – `references.md` (manuals and links), `verified-hardware.md` (what was tested on), tools reference, programming-guide notes, manual testing guide

Commands: `npm run build`, `npm test`, `npm run test:coverage` (writes `coverage/lcov.info`; CI uploads it to Codecov from one job, informational only, see `codecov.yml`), `npm run inspector`.

## Rules

- Commit as reid@malmoset.com (repo-local git config; check before committing).
- Sign commits (already configured globally); signing is encouraged but not required of contributors.
- Push issue branches and open PRs as described under Process. The maintainer has authorized merging green PRs into `main`. Do not tag, create releases, or bump versions without explicit go-ahead.
- Do not bump version numbers unless asked. Releases follow `docs/releasing.md` (GitHub release with tarball + GHCR image; npm is optional). User-visible changes add a line under `## [Unreleased]` in `CHANGELOG.md` in the same PR. Keep `package.json` free of npm auto-corrections (e.g. no `./` in `bin`); CI's `package contents`, install, git-install and docker smoke jobs guard the published package.
- Never commit secrets, device IPs/serials, or `.mcp.json`.
- **The analyzer locks its front panel in remote mode.** Do not send `:KEY:` commands or queries (not `:KEY:LED?`, not `:KEY:LOCK?`) and do not use `:SYSTem:LOCK?`/`:KEY:LOCK?`/`:KEY:LED?` as lock checks: the readbacks are unreliable. On the UTS3036B V1.04.0040 the first non-common command locks the touch screen and buttons until the physical Esc key is pressed, and `:SYSTem:LOCK 0`, VXI-11 `device_local`/`device_unlock` and `:KEY:ESC` do not return it to local (docs/verified-hardware.md, "Front-panel lock"). At the end of every live run tell the owner: "press Esc on the analyzer to return it to local mode".
- Keep each task/issue small enough to finish in one context window; split larger work.
- Every new tool needs an integration test with a mocked connection and a `### \`tool_name\`` section in `docs/tools-reference.md` (a test fails if a registered tool is undocumented).
- Every new, renamed or removed tool also needs its entry in `mcpb/manifest.json` (the Claude Desktop bundle); `tests/unit/mcpb-manifest.test.ts` fails if the manifest tool list differs from the registered tools. See the bundle section of `docs/releasing.md`.

## Process

- **Issues first.** Work is tracked as GitHub issues: one roadmap/epic issue plus small task issues. Do not start a task without an issue.
- **Task sizing.** Each task must fit in one context window: one tool group or one module, with its tests and docs. Split anything larger.
- **Test-driven.** For every task: write failing tests first (commit them or keep them in the same PR as the first commit), then implement until green, then refactor. Tests use a mocked connection; hardware checks are separate, manual, and recorded in `docs/verified-hardware.md`.
- **Incremental commits.** One logical change per commit (tests, implementation, docs may be separate commits), each building and passing on its own, so a person can audit the history.
- **Issue → work → PR.** Every PR must be tied to an issue: open the issue first, do the work on branch `issue-<n>-<slug>` from `main`, then open one PR with `Closes #<n>`. No PR without an issue. Each issue gets its own new branch, and its work reaches `main` only by merging that PR; never commit or push issue work directly to `main`.
- **Required checks follow the workflows.** The `protect-main` ruleset (id 26951437) requires 21 status checks, listed in docs/releasing.md ("Required status checks on `main`"); `codecov/*` and CodeRabbit are not required. Whenever a job in `ci.yml` or `codeql.yml` is renamed, added or removed, or its matrix (OS/Node/language) changes, update the docs list in the same PR (`tests/unit/required-checks.test.ts` enforces it) and have the ruleset's required checks updated (exact `gh api` steps in docs/releasing.md), or merges block forever on a check that never reports. Never require a path-filtered job. The admin bypass (pull_request mode) still exists: never use it to merge a red PR; all checks including CodeQL must be green with zero open code-scanning alerts before any merge.
- **Privacy.** Never put device serial numbers or real IP addresses in the repo, issues, or PRs.

## Concurrency (required for every tool)

MCP clients may issue parallel tool calls, and the analyzer has one command stream, one global error queue and ignores commands during a single sweep. So **each tool's whole operation is one exclusive session**:

- **Register every tool with `defineTool`** (`src/tools/util.ts`), never `server.tool()`/`registerTool()`. `defineTool` runs the handler inside `connection.runExclusive` (FIFO, nested helper calls join the session through AsyncLocalStorage, so helpers like `applyCommands` never deadlock), turns a busy timeout or any thrown error into an `isError` result, and `createServer()` makes `server.tool`/`registerTool` throw, so a bypass fails at startup and in the tests (`tests/integration/tool-contract.test.ts` also scans `src/tools` and checks every instrument operation ran inside a session).
- Put pure input validation (no instrument access) in the `validate` option of `defineTool` so an invalid call is refused without waiting for a long sweep. `exclusive: false` is for `disconnect`, `discover_instruments` and `list_instruments`. `defineTool` adds the optional `instrument` argument to every tool's schema (`instrumentArg: false` opts out) and `instrumentArg` (connect, disconnect, identify: the `name` argument) runs the handler with that instrument selected; `connect` registers a new name (`create`).
- Do not hold the session across user-visible waiting that is not needed, and do not start work that outlives the handler (fire-and-forget calls would escape the lock). A tool that starts a sweep must also wait for it inside the same handler.
- Tests: add the tool to the `CONTRACT` table; the contract test then also runs it in parallel mode (three copies at once and all tools at once, failures attributed to the owning call). Tests that mock `src/connection.js` with a hand-made object must provide `runExclusive: (fn) => fn()`.
- The wait limit is `UTS_BUSY_TIMEOUT_S` (default 120 s). Wiki pages that describe tool behavior or error handling should state the guarantee (issue #70).

## Error handling standard

Required for every tool that talks to the instrument. `tests/integration/tool-contract.test.ts` enforces it: it runs every registered tool against the fake connection in `tests/toolContract.ts` under not-connected, timeout, write failure, garbage/empty reply, instrument error and part-way failure modes. **A new tool must be added to the `CONTRACT` table in `tests/toolContract.ts` (kind, valid args, invalid args, args that must produce a warning) or that test fails.** Add canned replies for any new query to `QUERY_REPLIES` there.

1. **Tools never throw.** Every handler wraps everything in try/catch and returns `errorResult(...)` (isError, actionable message: what failed, which command, what to do next). No unhandled promise rejections, including fire-and-forget calls (use `.catch`).
2. **Setters:** validate input first (nothing is sent if invalid), then `applyCommands` (`*CLS`, each command synced with `*OPC?`, `:SYSTem:ERRor?` checked), then read the state back through `readBack(...)` and report every requested value, flag or enum the instrument did not take as a `warnings` entry (this unit clamps silently; check auto flags too). Failures go through `setterFailure(err, "get_x")`: instrument errors carry their code and text and say the settings may be partially applied.
3. **Getters:** parse every reply with `queryNumber` / `queryBool` / `queryParsed` (`src/instrument.ts`); a malformed or empty reply is a `ReplyError` naming the command and quoting the reply. A timeout names the command. A getter that fails part-way returns an error, never partial data.
4. **Multi-step operations** that change temporary state use try/finally to restore it; if restoring fails, say so. If a tool deliberately leaves state changed (e.g. `single_sweep` leaves single mode), failures say so.
5. **Connection problems** (not connected, closed, timeout, write failure) each have a distinct message; not-connected tells the user to call `connect`. A connection lost mid-operation names the command in flight, and `applyCommands` lists the commands that may already be applied (including the one in flight). The standard was checked on real hardware in issue #63 (see `docs/verified-hardware.md`).
6. **Hardware behavior** (clamp vs error vs ignored) is documented per tool in `docs/verified-hardware.md`.
7. **Every tool has failure-mode tests**, not only happy paths (the contract test covers the common modes; add tool-specific ones next to the tool's tests).
