# Releasing

How releases of `uni-t-uts-mcp` are made. Tagging and creating releases are maintainer decisions;
contributors and agents prepare changes but do not bump versions, tag or release without the
maintainer's explicit go-ahead (see [AGENTS.md](../AGENTS.md)).

**Release channels.** The package is on the npm registry (0.1.0 was published once from CI with provenance), so a
release is:

> After bumping the version, run `npm run clients:sync` (the per-client snippets in the README, site and wiki, and the Claude Code plugin files under `plugins/uni-t-uts`, embed the version); `npm test` fails while they are out of date.

1. a **GitHub release** for the tag `v<version>` with the packed tarball `uni-t-uts-mcp-<version>.tgz` and the
   Claude Desktop MCP bundle `uni-t-uts-mcp-<version>.mcpb` attached and the changelog section as notes, and
2. a **Docker image** `ghcr.io/reid-n0rc/uni-t-uts-mcp:<version>` on GHCR, and
3. an **npm package** `uni-t-uts-mcp@<version>` published by `npm-publish.yml` for the same tag; see "npm publishing".

## How users install a release

```sh
# From the npm registry (npx downloads and runs it):
npx -y uni-t-uts-mcp

# From the release tarball (the same files, fetched from GitHub):
npx -y https://github.com/Reid-n0rc/uni-t-uts-mcp/releases/download/v<version>/uni-t-uts-mcp-<version>.tgz

# Straight from the git tag (npm clones the repository and builds it through the `prepare` script, which needs git):
npx -y github:Reid-n0rc/uni-t-uts-mcp#v<version>

# Docker:
docker run -i --rm -e UTS_IP=192.168.1.100 ghcr.io/reid-n0rc/uni-t-uts-mcp:<version>
```

In an MCP client configuration use `"command": "npx"` with `"args": ["-y", "<one of the specs above>"]`
(on Windows clients that cannot launch `npx` directly: `cmd /c npx -y ...`). Newer npm versions may ask to allow the
install script of a git dependency; the tarball URL has no install scripts and is the most robust choice.

## The Claude Desktop bundle (`.mcpb`)

`release.yml` also builds `uni-t-uts-mcp-<version>.mcpb` (issue #86) and attaches it next to the tarball. It is a zip
made by the official packer `@anthropic-ai/mcpb` (version pinned in `scripts/build-mcpb.mjs`, fetched from npm into a
temporary folder; it is not a dependency of the project) from `mcpb/manifest.json`, `build/**/*.js`, the production
dependencies (`npm ci --omit=dev --ignore-scripts`), `package.json`, `LICENSE`, `README.md` and a generated `icon.png`.
Users double-click it in Claude Desktop; see the README for the settings dialog.

- The manifest `version` must equal `package.json`; the build stops otherwise. A test also keeps the manifest's tool
  list equal to the registered tools, so adding or renaming a tool means updating `mcpb/manifest.json` in the same PR.
- Local build: `npm ci && npm run build && npm run build:mcpb` writes `dist/uni-t-uts-mcp-<version>.mcpb`.
  `npm run test:mcpb` builds it again, checks the file list (no source maps, tests, docs, secrets, addresses or serial
  numbers), validates the manifest with the official validator, unpacks it into an empty folder and runs its entry
  point over stdio (`initialize` and `tools/list`, via `scripts/smoke-mcp.mjs`).
- CI: the `mcpb bundle` job does the same on Ubuntu, macOS and Windows for every pull request.
- The bundle is not signed (signing needs a code-signing certificate; the packer's `sign` command can add one later).
- v0.1.0 has no `.mcpb`; v0.2.0 is the first release that carries `uni-t-uts-mcp-0.2.0.mcpb`, and the README, site and
  wiki point at it.
- Manual check before announcing it (CI cannot run Claude Desktop): on macOS and on Windows, double-click the downloaded
  file, confirm the settings dialog shows Analyzer address (empty is allowed), Port (5025) and Transport (raw), install,
  start a new chat, check that the tools are listed under the extension, and ask "connect to the analyzer at
  <address>" (or enter the address in the settings and ask for the identification). Confirm nothing else needs to be
  installed on a machine without Node.js.

## The Claude Code plugin (`plugins/uni-t-uts`)

The repository is a Claude Code plugin marketplace (issue #87): `.claude-plugin/marketplace.json` (static) lists the plugin
`uni-t-uts` at `./plugins/uni-t-uts`. Its `.claude-plugin/plugin.json` (`version`, user config) and `.mcp.json`
(`npx -y uni-t-uts-mcp@<version>`) are generated by `npm run clients:sync` from the `package.json` version, so a
version bump touches them (run `npm run clients:sync`; `clients:check` and `tests/unit/claude-plugin.test.ts` fail
while they are stale). Because the pin names an exact npm version, the plugin only works once that version is on npm:
merge the version PR, tag, wait for `npm-publish.yml`, and only then tell users to update the plugin. Users receive
the new version when they update the marketplace (`/plugin marketplace update`), since `plugin.json` sets `version`.
Check before announcing: `claude plugin validate .` and `claude plugin validate plugins/uni-t-uts`, then
`claude plugin marketplace add Reid-n0rc/uni-t-uts-mcp && claude plugin install uni-t-uts@uni-t-uts-mcp` on a clean
machine and ask for the analyzer identification. Adding or renaming a tool needs no plugin change.

## Version policy

- [Semantic Versioning](https://semver.org/). The first release was **0.1.0**.
- Pre-1.0 (`0.y.z`) policy:
  - **New tools ship in minor releases** (0.2.0, 0.3.0, ...).
  - **Fixes, documentation-only and internal changes ship in patch releases** (0.2.1).
  - **Breaking changes** to tool names or parameters are announced under "Changed" in the changelog and also raise the
    minor version (never a patch release). Result shapes and environment variables follow the same rule.
  - 1.0.0 is cut when the tool set and its results are considered stable.
- The version lives only in `package.json` (`src/server.ts` reads it at runtime). The git tag is `v<version>`,
  for example `v0.1.0`. Pre-release tags use a hyphen (`v0.2.0-rc.1`): they create a GitHub pre-release and do not move the Docker
  `latest` tag.
- Fix forward with a new patch release instead of re-using a version number (an npm version, once published, is immutable).

## Changelog

[CHANGELOG.md](../CHANGELOG.md) follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Every
user-visible change adds a line under `## [Unreleased]` in the same PR (groups: Added, Changed, Deprecated,
Removed, Fixed, Security). The release step renames `Unreleased` to the version and date and opens a new empty
`Unreleased` section. The text of the version's section becomes the GitHub release notes (`release.yml`); without
a matching section the notes are generated by GitHub from the merged PRs. To draft entries from merged work:
`gh pr list --state merged --search "merged:>YYYY-MM-DD" --json number,title`.

with `--admin`.

### Keeping the ruleset in step with the workflows

Whenever a job in `.github/workflows/ci.yml` or `codeql.yml` is renamed, added or removed, or its matrix (OS, Node
versions, languages) changes, update the ruleset **in the same change**, or merges block forever on a check that never
reports (or a new job goes unenforced). `tests/unit/required-checks.test.ts` fails until the list above matches the
workflows; the ruleset itself needs the owner (or an admin) to apply it:

```sh
# read the current required checks
gh api repos/Reid-n0rc/uni-t-uts-mcp/rulesets/26951437 -q '.rules[]|select(.type=="required_status_checks")|.parameters.required_status_checks[].context'
# save the full ruleset, edit .rules[].parameters.required_status_checks (one {"context": "<name>"} per check)
gh api repos/Reid-n0rc/uni-t-uts-mcp/rulesets/26951437 > ruleset.json
# send back only name, target, enforcement, bypass_actors, conditions and rules
jq '{name,target,enforcement,bypass_actors,conditions,rules}' ruleset.json > ruleset-put.json   # after editing
gh api -X PUT repos/Reid-n0rc/uni-t-uts-mcp/rulesets/26951437 --input ruleset-put.json
```

Do not make a check required before it has reported on a pull request at least once, and apply a removal or rename
right after the workflow change merges (or before, when the old name would otherwise never report).

## Simulator conformance (issue #147)

The simulator (`tests/fakeUts.ts`) is only useful if it behaves like the analyzer. `scripts/conformance-lib.mjs` holds one
scripted SCPI exchange (about 65 steps: frequency, amplitude, bandwidth, detector, markers, the tracking generator state,
formats, error handling and an unsupported query) that runs unchanged against both:

- **The simulator, always, in CI:** `tests/e2e/conformance.test.ts` runs it and requires the transcript to equal the
  committed `tests/fixtures/conformance/exchange.txt` (about 7 s, mostly the wait for the late `-113`). Unit tests of the
  recorder, redactor and differ are in `tests/unit/conformance.test.ts`.
- **A real analyzer, on demand only:** `scripts/conformance.mjs`. It refuses to run unless `UTS_IP` and
  `UTS_CONFORMANCE_LIVE=1` are set, and never when `CI` is set.

```sh
UTS_IP=192.168.1.100 UTS_CONFORMANCE_LIVE=1 node scripts/conformance.mjs [--out transcript.txt] [--record]
```

(PowerShell: `$env:UTS_IP = "192.168.1.100"; $env:UTS_CONFORMANCE_LIVE = "1"; node scripts/conformance.mjs`.)

**Before you run it:** the first query puts the analyzer into remote mode and locks its touch screen and buttons until the
owner presses Esc on the analyzer, so tell the owner. The script sends only what is in `EXCHANGE` (no `*RST`, `:KEY:`,
`:SYSTem:LOCK`, `:SYSTem:DEFault`, LAN or `:MMEMory` commands), reads every setting it touches first (`RESTORE_PLAN`), writes
it back at the end, verifies the readback and checks that `:SYSTem:ERRor?` is clean. Serial numbers, IPv4 and MAC addresses are
redacted from the transcript (`<serial>`, `<ip>`, `<mac>`).

**Reading a diff.** Each difference shows the step number, the command, the committed reply and the analyzer's reply. Exit
status 0 means no unexplained difference and a clean restore. For every difference decide:

1. the simulator is wrong: fix `tests/fakeUts.ts` (and its unit test) so it reproduces the analyzer, cite the finding in
   `docs/verified-hardware.md`;
2. the analyzer is not reproducible (depends on the signal, the unit or its firmware): remove or change the step, or add an entry
   to `KNOWN_DIVERGENCES` in `scripts/conformance-lib.mjs` (`{cmd, actual: <regex of the analyzer's reply>, note}`); such a
   difference is printed as `known` and does not fail the run, but the note must say why.

**Refreshing the transcript.** After a deliberate change to `EXCHANGE`, or a firmware update, run the live script with `--record`
(it rewrites `tests/fixtures/conformance/exchange.txt` from the analyzer), review `git diff` of the fixture, make the simulator match
and commit them together; `npm test` then proves the simulator equals the committed transcript. Add the result to
`docs/verified-hardware.md`.

**Self-hosted runner (optional, not enabled).** The live run needs a runner on the analyzer's network. A manual job would be:

```yaml
on: workflow_dispatch
jobs:
  conformance:
    runs-on: [self-hosted, uts-bench]
    steps:
      - uses: actions/checkout@<pinned sha>
      - run: node scripts/conformance.mjs
        env: { UTS_IP: "${{ secrets.UTS_IP }}", UTS_CONFORMANCE_LIVE: "1" }
```

The script refuses when `CI` is set, so such a job would have to unset it; do that only on a bench runner whose owner accepts the
remote-mode lock. The address stays in a secret, never in the repository.

## Hardware checklist (live runs)

Before a release that changes tools or transports, run [manual-testing-guide.md](manual-testing-guide.md) (every tool group, raw and VXI-11, with restore steps and a reporting template) on a real analyzer, and record new findings in verified-hardware.md.

- Record the instrument state first (frequency, span, sweep mode, format) and restore it afterwards; `:SYSTem:ERRor?` must be clean.
- Do not send `:KEY:` commands or queries. The analyzer locks its front panel while in remote mode: at the end, run `node scripts/check-panel-lock.mjs` (a screenshot check) and tell the owner to press Esc on the analyzer only if it reports the panel locked. See "Front-panel lock" in docs/verified-hardware.md.
- No serial number or real IP address in anything committed.

## What the CI smoke tests cover

Pull requests and `main` run these in addition to the test matrix (`.github/workflows/ci.yml`), so a broken
package is caught before a tag exists:

| Job | What it checks | Local equivalent |
|-----|----------------|------------------|
| `package contents` | `npm pack --dry-run --json` lists only `build/**/*.js`, `build/**/*.d.ts`, `README.md`, `LICENSE`, `package.json` (no tests, docs, scripts, sources, source maps, `node_modules`); `npm publish --dry-run` makes no `package.json` auto-corrections (for example a dropped `bin`, which a `./` prefix in `bin` caused) | `npm run build && node scripts/check-pack.mjs` |
| `npm install smoke` | packs the tarball, installs it (`file:` spec) into an empty project on Ubuntu (Node 22 and 24), macOS and Windows, starts the installed `bin` over stdio, sends `initialize` and `tools/list`, and asserts the server name and that the tool count equals the number registered in the repo's build (never hard-coded) | see below |
| `git install smoke` | installs a `git+file://` URL of the checkout into an empty project (the code path of `npx github:...`, which builds through `prepare`), runs the bin over stdio and repeats the checks. The `github:` spec itself can only be verified once a tag exists | see below |
| `mcpb bundle` | builds the `.mcpb` on Ubuntu, macOS and Windows, validates the manifest with the official validator, checks the exact file list, and starts the unpacked bundle over stdio | `npm run build && npm run test:mcpb` |
| `docker image smoke` | builds the image (no push), checks the `org.opencontainers.image.source` label, runs it through `docker run -i` and repeats the same checks | `docker build -t uni-t-uts-mcp:ci . && node scripts/smoke-mcp.mjs -- docker run -i --rm uni-t-uts-mcp:ci` |
| `dependency audit` | `npm audit --omit=dev --audit-level=high` (runtime dependencies; fails on high or critical advisories). It also runs from a weekly schedule, when it is the only job, so new advisories surface without a pull request | `npm audit --omit=dev --audit-level=high` |

Local run of the install smoke test (POSIX shell, from the repo root after `npm run build`):

```sh
d=$(mktemp -d) && npm pack --silent --pack-destination "$d" && mkdir "$d/project" && (cd "$d/project" && npm init -y >/dev/null && npm install "$d"/uni-t-uts-mcp-*.tgz) && (cd "$d/project" && node "$OLDPWD/scripts/smoke-mcp.mjs" -- node_modules/.bin/uni-t-uts-mcp)
```

`scripts/smoke-mcp.mjs [--expect-tools N] -- <command> [args...]` is the generic checker; its logic is
unit-tested in `tests/unit/release-scripts.test.ts`.

## Maintainer-only setup (once)

Only what needs the maintainer's GitHub account; agents cannot do these.

1. **GHCR visibility.** The image is `ghcr.io/reid-n0rc/uni-t-uts-mcp` (lower case). It carries the
   `org.opencontainers.image.source` label, so the package is linked to this public repository and inherits its
   visibility. After the first push open the repository's Packages > `uni-t-uts-mcp` > Package settings: visibility
   must be Public (change it there if it is not) and "Manage Actions access" should list this repository with the
   Write role.
2. Repository settings: Actions enabled; workflow permissions may stay at the default read-only (each workflow
   requests what it needs; `release.yml` asks for `contents: write`, `docker-publish.yml` for `packages: write`).

## Release steps

1. Make sure `main` is green and the changelog's `Unreleased` section is complete.
2. **Version PR** (branch `release-<version>`): set `version` in `package.json` (and `package-lock.json`:
   `npm version <version> --no-git-tag-version`), rename `## [Unreleased]` in `CHANGELOG.md` to
   `## [<version>] - <YYYY-MM-DD>`, add a fresh empty `## [Unreleased]` above it, and update the compare links at the
   bottom of the changelog. Flip any docs that say "after the first release" to the real instructions. Open the PR,
   wait for every check (including the smoke jobs), merge.
3. **Dry run on the merge commit**: `git switch main && git pull`, `npm ci && npm run build && node scripts/check-pack.mjs`.
4. **Tag** the merge commit (the tag must equal `v` + the `package.json` version, otherwise the workflows stop with a
   clear error): `git tag -s v<version> -m "v<version>" && git push origin v<version>` (use `git tag -a` if you do
   not sign tags).
5. **Watch** the workflows that the tag triggers (Actions tab, or `gh run watch`).
6. **Verify** the published artifacts from a clean folder (below).

## What a `v*` tag triggers

| Workflow | Result |
|----------|--------|
| `release.yml` | checks the tag equals `v<package.json version>`, builds, tests, checks and smoke-tests the tarball, creates the GitHub release with the matching CHANGELOG section as notes (generated notes if there is none; hyphenated tags are marked pre-release) and attaches `uni-t-uts-mcp-<version>.tgz` and the `.mcpb` bundle (built and checked first); needs only `contents: write` |
| `docker-publish.yml` | checks the tag, builds `linux/amd64` and `linux/arm64`, pushes `ghcr.io/reid-n0rc/uni-t-uts-mcp` tagged `<version>`, `<major>.<minor>` and (not for pre-releases) `latest`, with OCI labels including `org.opencontainers.image.source` |
| `npm-publish.yml` | with no `NPM_TOKEN` secret: succeeds with a notice and publishes nothing. With the secret: checks the tag, builds, re-checks the tarball and runs `npm publish --provenance --access public` |

Nothing is published by pull requests or pushes to `main`. Every workflow action is pinned to a full
40-character commit SHA with the version as a trailing comment (`uses: actions/checkout@<sha> # v7`), and Dependabot's
`github-actions` ecosystem bumps both the SHA and the comment. `tests/unit/workflow-pinning.test.ts` fails on any unpinned
`uses:` (local `./` and `docker://` references are exempt).

### Actions policy (repository settings)

The Actions settings are reproducible with `gh api`: allowed actions are **selected** (GitHub-owned `actions/*` and `github/*`
plus `docker/*`; verified-creator actions off), fork pull request workflows need approval for all outside contributors, the
default `GITHUB_TOKEN` is read-only and Actions cannot approve pull requests. `sha_pinning_required` is turned on
(`gh api -X PUT repos/Reid-n0rc/uni-t-uts-mcp/actions/permissions -F enabled=true -f allowed_actions=selected -F sha_pinning_required=true`),
so any workflow that uses a tag instead of a SHA fails to start. Roll back with `-F sha_pinning_required=false`. The tag-triggered
workflows (release, docker, npm) are only exercised by a real tag: watch the runs of the next release.

## Verify a release

From an empty folder, ideally on a machine that has never run the project:

```sh
mkdir /tmp/verify && cd /tmp/verify
gh release view v<version> --repo Reid-n0rc/uni-t-uts-mcp      # notes present, tarball attached
npx -y https://github.com/Reid-n0rc/uni-t-uts-mcp/releases/download/v<version>/uni-t-uts-mcp-<version>.tgz
npx -y github:Reid-n0rc/uni-t-uts-mcp#v<version>
docker pull ghcr.io/reid-n0rc/uni-t-uts-mcp:<version>
docker run -i --rm ghcr.io/reid-n0rc/uni-t-uts-mcp:<version>
```

Each server start prints `uni-t-uts-mcp server running on stdio` on stderr (Ctrl-C to stop). For a protocol-level
check use the smoke script from a checkout of the tag, for example
`node scripts/smoke-mcp.mjs -- npx -y https://github.com/Reid-n0rc/uni-t-uts-mcp/releases/download/v<version>/uni-t-uts-mcp-<version>.tgz`
and `node scripts/smoke-mcp.mjs -- docker run -i --rm ghcr.io/reid-n0rc/uni-t-uts-mcp:<version>` (on Windows use
`npx.cmd`). Also confirm `docker pull ghcr.io/reid-n0rc/uni-t-uts-mcp:latest` works without logging in (public
visibility). Then update the README, site and wiki install sections from "after the first release" to the real
instructions.

## Rolling back or deprecating a bad release

1. **GitHub release and tag**: edit the notes with a warning (`gh release edit v<bad> --notes "..."`) or, when nothing
   should use it, delete it: `gh release delete v<bad> --yes --cleanup-tag` (or
   `git push --delete origin v<bad> && git tag -d v<bad>`). Never re-push a tag of the same name for different
   content; `npx github:...#<tag>` users and caches would get inconsistent results.
2. **Fix forward**: release the next patch version through the normal steps.
3. **Docker (GHCR)**: GHCR has no "deprecated" flag. Mark a bad image by re-pointing `latest` and `<major>.<minor>`
   to the good image (re-run the Docker workflow for the good tag: Actions > Publish Docker image > Re-run), and
   either delete the bad version (Packages > `uni-t-uts-mcp` > Package versions > Delete, which also removes every tag
   pointing at it) or leave it and state in the GitHub release notes that it is withdrawn.
4. **If npm was in use** (see below): `npm deprecate uni-t-uts-mcp@<bad> "Broken: use <good> instead"` (needs publish
   rights; a range such as `uni-t-uts-mcp@"<0.1.1"` works; undo with an empty message), and
   `npm dist-tag add uni-t-uts-mcp@<good> latest` to move `latest`. `npm unpublish` is only for leaked secrets or
   malware and only within npm's unpublish window.

If a workflow fails half-way (for example the release exists but the Docker push failed), fix the cause and re-run only
the failed workflow from the Actions tab; `release.yml` uploads the tarball to an existing release instead of failing.

## npm publishing

`uni-t-uts-mcp` is on npm: 0.1.0 was published once from CI (the `v0.1.0` tag workflow `npm-publish.yml`, with SLSA
provenance), and its `dist.shasum` is identical to the GitHub release tarball. Every later `v*` tag publishes the same
way (`npm publish --provenance --access public`; the workflow already has `id-token: write`) once trusted publishing is set up.

- **Authentication: trusted publishing.** The maintainer revoked the npm token and the `NPM_TOKEN` secret is deleted, so
  publishing relies on npm trusted publishing (OIDC, no token, no `NODE_AUTH_TOKEN`). `npm-publish.yml` publishes when
  either the secret `NPM_TOKEN` exists or the repository variable `NPM_TRUSTED_PUBLISHING` is `true`. One-time setup:
  1. On npmjs.com open the package `uni-t-uts-mcp` > Settings > Trusted Publisher > GitHub Actions and enter
     user/organization `Reid-n0rc`, repository `uni-t-uts-mcp`, workflow filename `npm-publish.yml`, and leave the
     environment empty.
  2. Run `gh variable set NPM_TRUSTED_PUBLISHING --body true` (in the repository).
  3. No `NPM_TOKEN` secret is needed any more.
  4. The next `v*` tag publishes with provenance.
  Optionally set the package to "Require two-factor authentication and disallow tokens".
- **Publishing is asynchronous.** npm now processes first publishes in the background: the CLI may print "Your package
  is being processed" and the registry may show a placeholder version `0.0.0-stage` for a few minutes. Verification must
  therefore poll `npm view uni-t-uts-mcp version` until the new version appears (for example once every 15 seconds for
  up to 10 minutes) instead of checking once.
- **Verify a release.** From a clean folder with an empty npm cache: `npm view uni-t-uts-mcp dist.shasum` must equal the
  shasum of the GitHub release tarball, and `npx -y uni-t-uts-mcp` must start the server (it logs
  `uni-t-uts-mcp <version>` on stderr and waits on stdio).
