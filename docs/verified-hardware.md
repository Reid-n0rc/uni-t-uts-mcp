## Command timing and error queue (2026-11-10, issue #45, firmware V1.04.0040)

- **Bursts:** several lines written in the same millisecond (e.g. `*CLS`, two setters, `:SYSTem:ERRor?`) can make the instrument queue spurious `-113 "Undefined header"` errors even though the settings are applied. The connection therefore follows every command with `*OPC?` and waits for the reply before writing again (`sendCommand(cmd, { sync: false })` opts out). 20 consecutive start/stop rounds produced no errors.
- **Stall after an unsupported query:** after a query the instrument does not recognize (no reply, `-113` queued) it stops responding for about 2.15 s and keeps only the last line received during that time. The connection holds the next job off until 2.5 s after the failed query was sent. Unsupported *commands* (no `?`) and a query sent within a few ms of the bad one are not affected.
- **`*CLS` clears the error queue**, which is global to the instrument and keeps stale errors from earlier unsupported queries. Tools that apply settings run `*CLS` first so only their own errors are reported.
- **One reply per burst of queries:** two queries written back-to-back (or joined with `;`) get one reply; send queries one at a time.
- **Late `-113` for unsupported queries (issue #47):** the error for an unsupported query lands in the error queue about 4 s after the query, even if `*CLS` ran in between (6 of 6 trials: `*CLS` after the hold-off read `0,"No error"`, and `-113 "Undefined header"` reappeared ~1.5 s later). Within 2 s of the bad query, an `:SYSTem:ERRor?` is itself lost to the stall. The connection records when a query last timed out (`msSinceQueryTimeout()`), and `applyCommands` ignores `-113` for 10 s after a timeout. Verified live: two bad `scpi_query` calls followed by `set_frequency` (center/span, start/stop, restore) reported no errors, twice.

## Amplitude (2026-11-10, issue #11, firmware V1.04.0040)

- **Queries** that reply: `:DISPlay:WINDow:TRACe:Y:RLEVel?`, `:PDIVision?`, `:SPACing?`, `:RLEVel:OFFSet?`, `:UNIT:POWer?`, `:POWer:ATTenuation?`, `:POWer:ATTenuation:AUTO?`, `:POWer:GAIN:STATe?`, `:SENSe:CORRection:IMPedance:INPut:MAGNitude?`. `:INPut:IMPedance?` gets no reply and `:INPut:IMPedance 50` is rejected as `-113`; the `:SENSe:CORRection:IMPedance:INPut:MAGNitude` alias works for both. Defaults seen: 0 dBm, 10 dB/div, LOGarithmic, offset 0, DBM, attenuation 10 (auto on), preamp off, 50 ohm.
- **Number format:** setters accept bare numbers and unit suffixes (`-10 dBm`, `5 dB`) alike; no error either way.
- **Out of range is clamped silently, no error:** reference level to -100..30 dBm; scale per division to 0.1..20; offset to +-327.6; attenuation to 0..51 and rounded to an integer (`7.6` -> `8`); impedance other than 75 reads back `50` (`60` -> `50`). An invalid enum (`:UNIT:POWer BOGUS`, `:SPACing BOGUS`) gives `-224 "Illegal parameter value"`.
- **Units:** `:UNIT:POWer` takes `DBM|DBMV|DBUV|V|W` (case-insensitive, the query returns upper case). The reference level reads back in the current unit (-10 dBm -> 36.9897 dBmV, 96.9897 dBuV, 0.0707 V, 1e-4 W; V assumes 50 ohm); the offset stays in dB. In linear scale the reference level is likewise read in the Y unit.
- **Attenuation:** setting a value turns auto off. `:POWer:ATTenuation:AUTO ON` (or `1`) turns it on, and the attenuation value then follows the reference level (0 dBm -> 10 dB, -30 dBm -> 0 dB; the value read immediately after turning auto on can still be the old one). Turning the preamp on with auto attenuation raised it from 10 to 30 dB.
- **Coupling:** the reference level readback includes the reference level offset (offset 2 dB reads 2 dBm for a 0 dBm level), and the maximum reference level depends on attenuation and preamp (20 dB manual attenuation with preamp on and a 2 dB offset: max -8 dBm). `set_amplitude` therefore sets preamp, attenuation and offset before the reference level.
- **Impedance 75:** set and read back as 75 (a correction; the reference level readback in dBm was unchanged); restored to 50.
- **Error queue backlog:** flooding the instrument with malformed lines left dozens of `-101 "Invalid character"` entries that outlast `*CLS`-less reads; `*CLS` then draining cleared them.
- All settings were restored afterwards (0 dBm, 10 dB/div, LOGarithmic, offset 0, DBM, auto attenuation, preamp off, 50 ohm); `:SYSTem:ERRor?` clean.

## Bandwidth, sweep, detector and trigger (2026-11-10, issue #12, firmware V1.04.0040)

- **Queries that reply:** `:SENSe:BANDwidth:RESolution?`, `:RESolution:AUTO?`, `:VIDeo?`, `:VIDeo:AUTO?`, `:VIDeo:RATio?`, `:SHAPe?`; `:SENSe:SWEep:TIME?`, `:TIME:AUTO?`, `:TIME:AUTO:RULes?`, `:TYPE?`, `:TYPE:AUTO?`, `:POINts?`; `:SENSe:DETector[:FUNCtion]?`, `:DETector:TRACe1..6?` and `:TRACe<n>:AUTO?`; `:TRIGger:SEQuence:SOURce?` and `:VIDeo:LEVel?` (also without `:SEQuence`). **No reply (unsupported):** `:TRIGger:SEQuence:EXTernal:SLOPe?`, `:EXTernal:DELay?` (also without `:SEQuence`) and `:DETector:TRACe7?`. Defaults: RBW/VBW 3 MHz both auto, ratio 1, GAUSsian, time 2.6475 ms auto (rule NORMal), type SWEep auto, 1001 points, all detectors NORMal with auto on, trigger IMMediate at -25 dBm.
- **Clamping, no error:** RBW and VBW clamp to 1 Hz..3 MHz and snap to 1-3-10 (50 kHz -> 30 kHz; 0 -> 1 Hz); VBW/RBW ratio clamps to 1e-5..3e6 (manual says 3e-7); sweep time clamps to 1 ms..4000 s at full span; points clamp to 11..40001 and non-integers truncate (1001.6 -> 1001); video trigger level clamps to -170..30 dBm. Invalid enums give `-224 "Illegal parameter value"`.
- **Coupling:** a manual RBW/VBW/sweep time turns its auto flag off. With VBW auto, VBW follows RBW times the ratio (manual ratio only matters while VBW is auto; it does not update when a manual VBW is set). Sweep time auto follows RBW, VBW, span and points (RBW 100 kHz at full span: 2.38 s; RBW 1 Hz: 3.9e7 s). RBW auto follows the span (1 MHz span -> 10 kHz). Setting a manual sweep time and then changing the span turned sweep time auto back on. Rule ACCuracy raised the automatic time from 2.6475 ms to 4.765 ms. Setting the points to 501 and back did not change the automatic time.
- **Sweep type FFT** is accepted (type auto turns off; sweep time changed to 82 ms); `:TYPE:AUTO 1` restores SWEep.
- **Detector:** SAMPle, POSitive, NEGative, NORMal and AVERage are all accepted on each trace. Setting a detector turns that trace's auto flag off; `:AUTO 1` returns it to the automatic choice (NORMal for a WRITe trace). Traces are independent. `:DETector:TRACe<n>:AUTO` exists on the 3000B although the manual lists it as 1000B only.
- **Trigger:** source accepts IMMediate and VIDeo; `EXTernal` gives `-224` and the source is unchanged. **Setting `:TRIGger:SEQuence:VIDeo:LEVel` switches the source to VIDeo**, so set the level first and the source after.
- All settings were restored (RBW/VBW auto 3 MHz, ratio 1, GAUSsian, time auto, SWEep auto, 1001 points, detectors NORMal/auto on all six traces, trigger IMMediate at -25 dBm, span 3.59 GHz, continuous sweep on); `:SYSTem:ERRor?` clean.

## Acquisition and sweep completion (2026-11-10, issue #13, firmware V1.04.0040)

- **`:INITiate:CONTinuous`** accepts `ON`, `OFF`, `1` and `0` (also mixed case); the query returns `1` (continuous) or `0` (single). No errors.
- **`:INITiate:IMMediate` and `:INITiate:RESTart`** work in spectrum-analyzer mode: in single mode each runs exactly one sweep (the trace is frozen afterwards; repeated trace reads return identical data), in continuous mode they are accepted without error. **`:INITiate:STOP`, `:PAUSe` and `:RESume` are unsupported**: `-113 "Undefined header"` in both modes, and the continuous sweep keeps running.
- **A single sweep takes the sweep time**: 6 s set -> 5.8 s measured from the command to the first answer (plus ~0.3 s my script slept), 3 s -> 2.8 s, 2 s -> 1.8 s; auto time (2.6 ms) returns immediately.
- **The instrument ignores commands while a single sweep runs (raw socket).** Every line sent during the sweep (queries, `*OPC?`, trace reads) is dropped, not queued: an `*OPC?` sent right after `:INITiate:IMMediate` got no reply even 20 s later (sweep time 6 s). Lines sent shortly before the end may be answered late, so a polling loop can see a duplicate `1`; the helper settles 100 ms afterwards. So `*OPC?` does **not** block until the sweep ends, and `:INITiate:IMMediate` followed by `*OPC?` is the wrong pattern (the `*OPC?` that the connection adds to every command would be lost and time out).
- **Chosen sync**: send `:INITiate:IMMediate` without `*OPC?` sync, stay silent for the sweep time read from `:SENSe:SWEep:TIME?`, then poll `*OPC?` (300 ms timeout, no hold-off); the first `1` means the sweep is complete. A timeout (default sweep time + 10 s) covers a sweep waiting for a video trigger. Tested end to end on hardware: `single_sweep` with a 5 s sweep time took 5.2-5.3 s; a 1 s timeout returned a clean error result and the instrument recovered after the sweep ended. Polling a trace or `:INITiate:CONTinuous?` cannot work for the same reason (queries are dropped while sweeping).
- Practical consequence: with a long sweep time in continuous mode most commands are dropped too, so set the sweep time back to auto before relying on other tools.
- Restored afterwards: continuous sweep ON, sweep time auto (2.6475 ms), `:SYSTem:ERRor?` clean.
- **SRQ / status-byte polling does not work (evaluated for T4).** Real SRQ interrupts are unavailable over raw TCP (they need VXI-11, HiSLIP or USB488), so the polled equivalent was tested: `*CLS`, `*ESE 1`, `*SRE 32` (both read back), single sweep (4 s), `:INITiate:IMMediate`, then `*OPC` (command form) and polling `*ESR?`/`*STB?`. Results: (1) `*OPC` and `*ESR?` sent while the sweep runs are dropped like every other line (the instrument ignores input during the sweep); (2) after the sweep, with `*OPC` sent while idle, `*ESR?` and `*STB?` were still `0`: this firmware never sets the operation-complete bit (ESR bit 0, STB bit 5), so there is nothing to wait for; (3) in continuous mode `*CLS`, `*OPC`, `*ESR?` also gave `0`. `*ESR?`/`*STB?` therefore carry no sweep information, and the only usable completion signal is the instrument answering again after the sweep. `*ESE`/`*SRE` were restored to 0.

## Error handling standard (issue #58)

Behavior by tool group, as implemented (mock tests, plus the live check below; see AGENTS.md "Error handling standard"):

- Setters never throw: invalid input is rejected before anything is sent; the instrument's clamping/snapping is not an error but is reported in `warnings` after a readback (numbers, and also units, scale type, preamp, filter shape, sweep type/rule, trigger source and the requested auto flags). Instrument-reported errors (`:SYSTem:ERRor?`) are errors that name the commands sent and say the settings may be partially applied. A failure part-way through (write failure, closed socket, error queue unreadable) lists the commands that were already sent.
- A timeout of `:SYSTem:ERRor?` itself is treated as "no information" (src/errors.ts), not as a failure; the readback comparison still catches wrong values.
- Getters parse strictly; an empty or malformed reply is an error naming the command and quoting the reply. `identify` requires four comma-separated `*IDN?` fields.
- `scpi_command` checks the error queue like other setters. `scpi_query` returns replies verbatim (text) and does not interpret them.
- `single_sweep` deliberately leaves the instrument in single sweep mode; its failure messages say so.

## Live check of the error handling standard (2026-11-10, issue #63, firmware V1.04.0040)

Run through the built server over stdio against the real analyzer (plus a local TCP proxy that can be cut, for the mid-operation failures). Everything was restored afterwards and `:SYSTem:ERRor?` ended clean.

- **Not connected:** all 17 other tools (every tool except `connect`/`disconnect`) return `Not connected to the spectrum analyzer. Use the 'connect' tool first.` and send nothing.
- **Instrument errors through `scpi_command`:** `:FREQuency:CENTer 1 XYZ` gives `-224 "Illegal parameter value"` plus `-131 "Invalid suffix"`; `:UNIT:POWer BOGUS` gives `-224` twice. Both are returned as an error naming the codes and the command, and the queue is clean afterwards (`*CLS` first, the errors are drained).
- **Unsupported query through `scpi_query`:** `Query timeout after <n>ms for command: <cmd>`. The next getter waits out the hold-off (about 1.6 s) and works; a setter right after (`set_frequency`) reported no error (the late `-113` is ignored for 10 s). The stale `-113` shows up in a later manual `:SYSTem:ERRor?` as documented above.
- **Clamping warnings (requested vs actual), all confirmed:** center 5 GHz -> 3.60999995 GHz, span 10 GHz -> 3.61 GHz, stop 5 GHz -> 3.61 GHz, reference level 100 -> 30 dBm and -500 -> -100 dBm, offset 1000 -> 327.6 dB, RBW 50 kHz -> 30 kHz, 0.4 Hz -> 1 Hz, 1 GHz -> 3 MHz, VBW 50 kHz -> 30 kHz, ratio 1e-7 -> 1e-5, sweep time 1 us -> 1 ms, video trigger level 100 -> 30 dBm. Center 100 kHz is accepted but the span shrinks to 100 Hz (coupling, not reported as a warning because the requested value was taken). Bandwidth/sweep/detector and amplitude arguments outside the tools' own validation (attenuation not an integer 0..51, impedance other than 50/75, scale per division above 20, points outside 11..40001) are rejected before anything is sent.
- **No spurious warnings from the readback checks (about 100 setter calls):** power unit (`dBm`, `dBmV`, `dBuV`, `V`, `W`; the instrument replies upper case and the tool maps it), scale type (linear/logarithmic), preamp on/off, `attenuation_auto` on/off immediately after being set (also right after a manual attenuation, a reference level change and turning the preamp on), impedance 75/50, RBW/VBW auto on/off, filter shape, sweep type fft/sweep with auto, rule, sweep time auto, points, trigger source, detector per trace with auto, `set_acquisition` continuous on/off, `center_step_auto`, offset, zero span and full span. Every warning that did fire was a real clamp (list above). No readback mismatch needed a tool fix.
- **Mid-operation connection failure** (local proxy cut at chosen points; the instrument itself was never disturbed): the instrument applies a command it received even if the connection then drops, so a failure message must not claim otherwise. Findings and fixes: (1) a reset socket gave the raw `Socket error: read ECONNRESET` while a clean close gave `Connection closed unexpectedly`; both are now `Connection to the spectrum analyzer was lost (<reason>) while sending|querying <command>`; (2) the call after a drop said `Not connected ... Use the 'connect' tool first` as if the user had never connected; it now says the connection was lost and to reconnect (an explicit `disconnect` still gives the plain message); (3) `applyCommands` did not name the command that was in flight when the failure happened, although it may have executed; it now says so; (4) `single_sweep` cut while switching to single mode left the analyzer in single mode (verified: `continuous: false` on the next session) without saying so; its message now says it may have been left in single sweep mode. Getters cut part-way return an error naming the query that was in flight, never partial data. Cutting during the readback of `set_amplitude` reported the command already sent (`PDIVision 5` was applied on the instrument and restored afterwards).
- Cosmetic fix: a warning for a unitless setting read `requested 1e-7 , now 0.00001` (stray space); it now reads `requested 1e-7, now 0.00001`.
- Restored afterwards: 10 MHz-3.6 GHz (center 1.805 GHz), continuous sweep, sweep time auto 2.6475 ms, 0 dBm, 10 dB/div, LOG, offset 0, DBM, auto attenuation (10 dB), preamp off, 50 ohm, RBW/VBW auto 3 MHz, 1001 points, detectors NORMal with auto, trigger IMMediate, `*ESE`/`*SRE` 0; `:SYSTem:ERRor?` returned `0,"No error"`.

## Concurrency (2026-11-10, issue #66, firmware V1.04.0040)

Parallel tool calls through the built server over stdio (one MCP client firing `Promise.all`), against the real analyzer. The lock is in the server, so what was checked is that the instrument's behavior does not get in the way: nothing was lost to the instrument ignoring commands during a sweep, and no error was misattributed.

- **Batch of 12 parallel calls** (`set_frequency` 1 GHz/100 MHz, `set_amplitude` -10 dBm, `get_frequency`, `get_amplitude`, two `scpi_query`, a `scpi_command` the instrument rejects (`:FREQuency:CENTer 1 XX`), `single_sweep`, more getters, a second `set_frequency`), then the same batch in reverse order: every call returned the correct, uncorrupted result with no warnings; each getter showed the values of the setter that came before it in the queue (calls run in arrival order); the rejected command was the only failure, reported with its own `-224` and `-131` errors and the command it sent; no other call saw them. `:SYSTem:ERRor?` afterwards: `0,"No error"`.
- **Busy limit:** with `UTS_BUSY_TIMEOUT_S=0.2` and a 1.5 s manual sweep time, `single_sweep` completed normally and a `get_frequency` fired 100 ms after it failed with `Instrument busy: waited 0.2 s for another tool call (single_sweep) ...`; the next `get_frequency` worked.
- A sweep started with `start_sweep` `wait=false` returns, and so releases the lock, while the instrument is still sweeping: a call made then is lost to the instrument (documented in the tools reference).
- Restored afterwards: 10 MHz-3.6 GHz, continuous sweep, sweep time auto, 0 dBm, 10 dB/div, LOG, offset 0, DBM, auto attenuation (10 dB), preamp off, 50 ohm, RBW/VBW auto, 1001 points, detectors and traces 1-6 as found (all seven getters compared equal before and after); `:SYSTem:ERRor?` clean.

## Trace configuration (2026-11-10, issue #14, firmware V1.04.0040)

Probed with raw SCPI, then through the built server (`get_trace`, `set_trace`, `restart_trace`, `set_trace_math`). Originals recorded first (trace 1-6 type WRITe, update/display 1,1,1,0,0,0, selected trace 1, average count 100, average type LOG) and restored afterwards; `:SYSTem:ERRor?` ended clean.

- **Queries that reply:** `:TRACe:SELect?`, `:TRACe<n>:TYPE?` (`WRITe`, `AVERage`, `MAXHold`, `MINHold`), `:TRACe:TYPE?` (current trace), `:TRACe<n>:UPDate:STATe?`, `:TRACe<n>:DISPlay:STATe?` (also `:DISPlay?`), `[:SENSe]:AVERage:COUNt?`, `:AVERage:TYPE?` (`VOLTage`, `POWEr`, `LOG`; with or without `:SENSe`). **No reply (unsupported, stalls ~2.15 s, posts `-113`):** `:CALCulate:MATH?` and the variants `:CALCulate:MATH:STATe?`, `:TYPE?`, `:TRACe?`, `:FUNCtion?`, `:TRACe<n>:MATH?`, plus `:TRACe0:TYPE?` and `:TRACe7:TYPE?`. Trace math is therefore write-only.
- **Rejected, not clamped (error and the old value stays):** `:TRACe:SELect 0` and `9` give `-224`; an unknown type or average type gives `-224`; `:TRACe7:TYPE ...` gives `-108`; `:CALCulate:MATH` with an offset of 200 gives `-224`, with `OFF` and no operands `-224`, with an unknown type `-108`.
- **Average count:** the instrument does **not** enforce 1-999: 0 becomes 1, 7.6 rounds to 8, **1000 is kept as 1000**. The tool validates integers 1-999 before sending. The count and type are global (not per trace).
- **Restart of hold/average (ambiguity 8), measured on a noise trace with max hold and averaging running (a freshly restarted max hold reads lower and climbs back over a few sweeps; a saturated one does not move):** re-sending `:TRACe<n>:TYPE <same type>` **restarts it**; so do `WRITe` then back, `:TRACe<n>:UPDate:STATe 0` then `1`, and re-sending `:AVERage:COUNt`. `:INITiate:RESTart` and `:INITiate:IMMediate` in continuous mode do **not** restart the hold, and with an average trace running they leave the instrument ignoring commands (queries time out) for roughly count x sweep time. A source change (tracking generator level) also restarts the hold, so a hold cannot be shown to survive a signal drop that way. `restart_trace` uses the re-send of the current type.
- **Hold behaves as expected on a real signal:** with the tracking generator on (looped to the input) max hold sat above the live trace (mean about 0.3 dB higher, smoothly flat) and the average trace was smoother (adjacent-point deviation 0.13 dB against 0.55 dB live). `:TRACe<n>:UPDate:STATe 0` freezes the trace (view/hold): it kept its data while the live trace followed the generator.
- **Trace math works** (verified through the trace data of the target trace): `PDIFference` and `PSUM` of a trace and a much weaker one both give about the stronger trace, `LDIFference` with +10 dB gave A-B+10 dB, `LOFFset` gave A (the offset was not visible in this arrangement, treat as unverified), `OFF` returns the trace to its live data. **Enabling math on a trace switches that trace on (update and display become 1); `OFF` leaves it on.**
- **`:trace1:mode write`** (the manual appendix example) gives `-113`; `:TRACe<n>:TYPE` is the right form. `:KEY:Default` was not sent.
- **Late error posting:** a rejected command can post its error well after `*CLS`: the first setter after a batch of rejected `:CALCulate:MATH` probes saw a stale `-109 "Missing parameter"` although the setting applied. A one-off stale error after probing is not a tool bug; re-running `:SYSTem:ERRor?` until `0` clears it.
- **Tracking generator side effects (found while testing, relevant to the tracking-generator tools):** `:OUTPut:STATe 1` makes the auto sweep time about 2.15 s (the instrument then drops most lines sent during the sweep in continuous mode). After `:OUTPut:STATe 0` the automatic RBW stayed at 300 kHz (auto sweep time 264 ms instead of 2.6475 ms) until `:SENSe:BANDwidth:RESolution:AUTO ON` was sent again, which restored 3 MHz; both auto flags still read 1 while stale.

## Trace data tool (2026-11-10, issue #15, firmware V1.04.0040)

Checked through the built server over stdio (`get_trace_data`) on both transports (`UTS_TRANSPORT=raw` and `auto`, which chose VXI-11). Originals recorded first and compared after: frequency 10 MHz-3.6 GHz, continuous sweep on, sweep time auto, amplitude, bandwidth (RBW/VBW auto), 1001 points, detectors, traces, `:FORMat` ASC8, picture format BMP, `*ESE`/`*SRE` 0, tracking generator off; `:SYSTem:ERRor?` clean.

- **Formats compared on one frozen trace** (single sweep, then `:TRACe1:UPDate:STATe 0`, so repeated reads are identical; 5 reads each): all three formats return 1001 values equal to `:SENSe:SWEep:POINts?`. **REAL32 equals ASCII exactly at the 7 significant digits ASCII carries** (maximum difference 0); REAL64 differs from both by at most 5e-5 dB, which is the ASCII/float32 rounding (a value such as -110.3427 has only 4 decimals). So REAL32 gives no precision over ASCII and REAL64 is the only exact format. Transfer time per tool call (including the settings queries and, for the binary formats, the format switch and restore): raw ASCII 175 ms, REAL32 242 ms, REAL64 236 ms; VXI-11 ASCII 143 ms, REAL32 160 ms, REAL64 165 ms. ASCII is faster because it needs no format round trips, hence **`ascii` is the default**; payload size (14 KB against 4 KB) does not matter on a LAN.
- **`:FORMat` is restored** after every binary read (`ASCii` setter, reads `ASC8`), also when the read fails; a final `:FORMat?` after each run was `ASC8`.
- **Zero span:** `:FREQuency:STARt?` and `:STOP?` both equal the center frequency, `:SENSe:SWEep:TIME?` is the span of the trace, so the tool returns a time axis. In zero span `set_frequency` with `start_hz`/`stop_hz` re-clamps to the center (the restore must use `full_span`), the center step becomes 3 MHz until span is restored, and afterwards `sweep_time_auto` read false and `sweep_type_auto` true (its original was false) while the settings were being put back; both were re-set to the originals, the cause was not isolated.
- **Tracking generator loopback** (generator level -30 dBm, `:OUTPut:STATe 1`; the generator output follows the sweep so the trace is a flat line, not a single peak): fresh reads showed min -30.9 dBm, max -27.8 dBm, mean -29.2 dBm, peak near 3.004 GHz, identical across ASCII, REAL32 and REAL64 within 0.1 dB (live sweep to sweep ripple) over both transports. The auto sweep time is 2.15 s with the generator on and the first read right after switching it on still saw the old 2.6 ms sweep time (the wait is by polling, so it still completed). Switched off afterwards and `:SENSe:BANDwidth:RESolution:AUTO`/`VIDeo:AUTO` re-asserted; RBW and VBW read 3 MHz.
- **`fresh`** took about the sweep time (0.28 s for a 2.6 ms sweep including the checks, 2.6 s with the generator on) and put continuous mode back on both transports; with continuous mode already off it stays off.
- **Decimation** to 100 points kept the global peak (identical `peak_index`) and returned in 160-220 ms.
## Markers (2026-11-10, issue #16, firmware V1.04.0040)

Probed by hand over raw SCPI, all marker state restored afterwards (all markers off, trace 1, reference marker n+1, peak criteria automatic, center/span, reference level and automatic center step back).

- **Queries that answer:** `:CALCulate:MARKer<n>:MODE?` (`OFF`, `POSition`, `DELTa`, `FIXed`), `:TRACe?`, `:X?`, `:Y?`, `:REFerence?`, `:CALCulate:MARKer:SELect?`, `:PEAK:THReshold?`, `:PEAK:THReshold:STATe?`, `:PEAK:EXCursion?`, `:PEAK:EXCursion:STATe?`. Markers 1-10 exist; `:CALCulate:MARKer11:MODE?` gets no reply (the usual stall and `-113`/`-108`), so the tools validate 1-10 themselves. Default reference marker of marker n is n+1 (marker 10: 1). Defaults seen: all modes `OFF`, trace 1, X 0.
- **Off markers:** `X?` returns the last position (stale) and `Y?` a level, even while the marker is off, so `get_marker` reports `null` for both.
- **A search turns a marker on:** `:MAXimum` on a marker whose mode is `OFF` sets it to `POSition` (resolves ambiguity 10). `:MAXimum:NEXT`, `:LEFT`, `:RIGHt` and `:MINimum` also work; `:MAXimum:LEFT`/`:RIGHt` on a live noisy trace can land on a peak on the other side of the marker, because the trace changes between sweeps.
- **`:PTPeak` leaves the marker in `DELTa` mode** with X and Y relative to its reference marker (for example marker 1 delta X -1.777 GHz, Y -22.75 dB from the minimum to the maximum).
- **Delta markers:** `X?` and `Y?` are **relative** to the reference marker (resolves ambiguity 10). `:REFerence <own number>` gives `-224` and keeps the old value; the reference was read back after setting 1.
- **Setters:** `:MODE` accepts `OFF|POSition|DELTa|FIXed` (a bad one gives `-224`); `:TRACe 9` gives `-224` and keeps the old trace; `:X` is **not clamped**: 5 GHz and 1 MHz read back unchanged on a 10 MHz to 3.6 GHz span (the tools therefore cannot warn about it from the readback; the level at such a position is not meaningful).
- **Setting `:REFerence` on a marker that is off turns it on in `DELTa` mode** (seen through the built `set_marker` tool, which then returned `mode: delta`; `markers_all_off` cleared it). `set_marker` with only `reference_marker` therefore also switches the marker on.
- **Marker to instrument** (`:CALCulate:MARKer<n>:SET:CENTer|STEP|STARt|STOP|RLEVel`): all five work and the targets read back the marker's values (center 1 GHz, start 2 GHz, stop 3 GHz, step 1 GHz, reference level -67.45 dBm). `:SET:STEP` turns automatic center step off. `:SET:CENTer` with a marker whose frequency would put the current span outside the range (marker at 1 GHz, span 3.59 GHz) gives `-224`, and the earlier command leaves frequencies as they were set by the other commands.
- **Peak criteria:** setting `:PEAK:THReshold <v>` or `:PEAK:EXCURSION <v>` turns the matching `:STATe` (automatic) to 0; `:STATe 1` switches it back and the value is then computed from the trace (it read -70.2 dBm and 5.9 dB). Clamping: threshold 50 reads 30, but -300 is accepted (the manual says -200 to 30), excursion 500 reads 200 and -3 reads 0 (the manual says 0 to 100); the tools validate the manual's ranges before sending.
- **Error queue** was clean after every accepted command; `:SYSTem:ERRor?` ended `0,"No error"`.

## VXI-11 transport (issues #64, #74; verified on hardware for issue #75, firmware V1.04.0040)

Everything below was measured on the real analyzer, through the built server over stdio where a tool is named, and with a small client on the VXI-11 core channel where the wire behavior is the point. Raw and VXI-11 were compared side by side.

**Basics.** The portmapper (TCP and UDP 111) registers the VXI-11 core, async and interrupt programs (395183, 395184, 395185) over TCP on a dynamic port. `create_link("inst0")` works, `maxRecvSize` is 1 MiB. HiSLIP (4880) is closed. True SRQ does not work: `create_intr_chan` and `device_enable_srq` succeed but the instrument never connects back, and `device_readstb` answers in about 1 ms with a status byte that stays 0x00 even with `*ESE 1` / `*SRE 48`, so the interrupt channel is not used.

**Every tool returns the same values over VXI-11 as over raw.** All getters (`identify`, `get_frequency`, `get_amplitude`, `get_bandwidth`, `get_sweep`, `get_detector`, `get_acquisition`, `get_trace`) returned identical results, and one scripted sequence through every setter (`set_frequency`, `set_amplitude`, `set_bandwidth`, `set_sweep`, `set_detector`, `set_trace`, `set_trace_math`, `restart_trace`, `set_acquisition`, `scpi_command`, `scpi_query`, including a clamped value and an invalid argument) gave identical results, warnings and errors on both transports. `connect` with `transport` `raw`, `vxi11` and `auto` works, `auto` picked VXI-11, and an explicit `port` with `vxi11` is refused before anything is sent.

**Reads: the instrument never answers a read that has nothing to deliver.** This drove the transport design:
- A `device_read` with a non-zero `io_timeout` and nothing to deliver is never answered with error 15. The instrument waits **5.4 times the io_timeout** (0.5 s gave 2.7 s, 1 s gave 5.4 s, 3 s gave 16.1 s, 6 s gave 32.3 s; linear), then drops the request without a reply, and it serves no other call on that link meanwhile: a `device_write` right after only completes when the instrument has given up. Nothing is lost, the write is delayed.
- A `device_read` with `io_timeout` 0 always answers error 15 at once, **even when a reply is waiting**. It cannot be used to poll or to drain.
- So the only working timeout is the client's RPC deadline. The transport sends a fifth of the requested timeout as `io_timeout` (the instrument then waits about 1.08 times the timeout, long enough for anything that arrives in time and free again about when the client gives up) and fails the read with `TransportTimeout` at the requested timeout plus a 500 ms RPC margin, keeping the link. The first version of the transport (io_timeout = timeout, error 15 expected) declared the link lost after every timed-out query and stalled the next write for several times the timeout; the fix is the code described here, with tests built on a fake that reproduces these rules.
- The output buffer has **one slot**: a second query written before the first reply was read replaces it (two stacked queries returned only the second reply), and the reply of a query whose read gave up never shows up in front of the next query's reply (checked mid-sweep and after a sweep). The old "read the leftover away before the next write" step is therefore gone.

**Unsupported query over VXI-11.** The read gets no reply and no error 15 (it would wait 5.4 times its io_timeout). The `-113 "Undefined header"` is in the error queue **at once** (about 1.6 s after the query, when the instrument is free again; over raw it appears about 4 s after), not late. Lines written meanwhile are not lost: a write is delayed until the instrument has given up the read, then executes. With the transport's one-fifth io_timeout that is about when the client gives up, so the next call runs at once (`*IDN?` 9 ms after a 1 s timeout, `get_frequency` 50 ms). A timed-out query reports `Query timeout after <T>ms ... (over VXI-11)` after T + about 0.5 s. A setter the instrument rejects (`:NOT:ACOMMAND 1`, a bad suffix) posts its error immediately: `:SYSTem:ERRor?` right after it, with no `*OPC?` in between, already shows it.

**Command bursts need no `*OPC?` pacing** (`syncsCommands` stays false): 40 unpaced `:SENSe:FREQuency:CENTer` writes took 71 ms and the readback was the last value; 30 rounds of set plus immediate query gave no mismatch; 10 rounds of RBW and VBW setters plus a query were correct; the error queue was empty. Each `device_write` returns in 1 to 3 ms.

**Sweeps** (`single_sweep`, single mode, one blocking `*OPC?` read; the table is the `waited_ms` of three runs each, raw next to VXI-11):

| Sweep time | raw | VXI-11 |
|-----------:|-----|--------|
| 0.1 s | 322, 329, 310 ms | 208, 186, 198 ms |
| 1 s | 1202, 1191, 1193 ms | 1119, 1108, 1111 ms |
| 4 s | 4244, 4240, 4250 ms | 4108, 4117, 4147 ms |
| 20 s | not measured | 20137, 20098 ms (`timeout_s` 30) |

The extra time is about 90 to 150 ms over VXI-11 (instrument overhead after the sweep) against 200 to 250 ms over raw. A deliberately too short timeout (`timeout_s` 1 for a 4 s sweep, and 0.2 s with `start_sweep` then `wait_for_sweep_complete`) fails with `Timed out: the sweep did not complete within 1.0 s (no reply to the blocking *OPC? read over VXI-11)` after 1.5 s (0.7 s for 0.2 s), the link stays up, and a `get_frequency` sent right after was **queued behind the running sweep and answered when it ended** (2.6 s later, correct value): nothing is dropped. Commands during a sweep are queued, as in the prototype (`dropsInputDuringSweep` stays false).

**Large transfers, and the screenshot works over VXI-11 (issues #42, #20).**
- `:TRACe:DATA? TRACE1` over ASCII: 14,015 bytes (1001 values) in 81 ms. REAL32 (`:FORMat REAL32`): `#44004` + 4004 bytes in 75 ms; REAL64: `#48008` + 8008 bytes. Same layout as over raw; `:FORMat` was set back with `ASCii` and reads `ASC8` again.
- **`:DISPlay:ZBmp?` is not truncated over VXI-11**: the full reply arrived, 200,687 and 202,462 bytes in two captures (`#9` + 9-digit length, `0x03`, a compressed BMP-like stream), in 54 ms, repeatably. Over raw the same query stops at exactly 144,800 bytes.
- **`:DISPlay:DATA?` is not truncated either**: `#7` + `4096054` followed by a complete uncompressed 1280 x 800, 32 bit BMP (4,096,054 bytes, 4,096,065 with header and CRLF) in 371 ms; it converts to a valid screenshot of the instrument screen. Over raw it times out.
- With `:SYSTem:PICture:FORMat PNG`, `:DISPlay:DATA?` returned a real PNG (`#590704` + 90,704 bytes, 3 s) over VXI-11, where raw returns nothing after PNG was selected. `:DISPlay:ZBmp?` still returns the BMP-like stream. The picture format was set back to `BMP`.
- Through the `scpi_query` tool with `reply: "block"` the three transfers worked over VXI-11 (the tool shows the first 64 KiB and marks larger replies as truncated) and timed out over raw.

**`screenshot` tool, live (issue #20).** Through the built server over VXI-11: `screenshot` returned an `image/png` block of 91,483 bytes in about 3.0 s, a valid 1280 x 800 capture of the instrument screen; `:SYSTem:PICture:FORMat?` read `BMP` before and after, and `:SYSTem:ERRor?` was clean. Over raw TCP (`UTS_TRANSPORT=raw`) the tool refused at once without sending anything (the 144,800 byte limit of issue #42), and the format stayed `BMP`. No captured image is stored in the repository because a screen can show the instrument's serial number or address.

**Links.** One client was killed with SIGKILL 12 times in a row (no `destroy_link`): every next connect worked at once, so the instrument frees a link when its TCP connection goes away. 40 links were open at the same time and all of them kept answering; no limit was reached. A raw TCP connection (port 5025) and a VXI-11 link work at the same time: interleaved and simultaneous queries on both got correct replies; while a sweep started over VXI-11 runs the raw connection gets no reply (as always), the VXI-11 `*OPC?` answers at its end. The instrument web page (port 80) kept answering while a link was open and queried. Vendor software was not available to test.

**Error paths over VXI-11 (the checks of issue #63 repeated), through the built tools** (the VXI-11 core channel went through a local TCP proxy, with a fake portmapper pointing at it): a setter the instrument rejects returns `The instrument reported errors: -224,"Illegal parameter value"; -131,"Invalid suffix" (after sending: ...)`, and the queue is clean afterwards; not connected gives `Not connected to the spectrum analyzer. Use the 'connect' tool first.`; cutting the connection at every RPC call of `set_frequency`, `set_amplitude` (including during the readback), `get_amplitude`, `get_detector`, `get_trace`, `scpi_command`, `scpi_query` and `single_sweep` (before the start command, before the `*OPC?` write, before its blocking read, and by destroying all sockets 1.2 s into a 3 s sweep) gave `Connection to the spectrum analyzer was lost (VXI-11: ... aborted: connection closed) while ...` naming the command, with the "may already be applied" hint for setters and sweeps, and every later call says to reconnect; a new link right after worked (the sweep continued on the instrument). Two batches of 12 parallel tool calls (setters, getters, a rejected command, `single_sweep`) were serialized by the session lock: all succeeded except the one rejected command, which failed alone.

**Capability flags confirmed** (`VXI11_CAPABILITIES`): `syncsCommands` false, `dropsInputDuringSweep` false, `holdOffAfterTimeout` false (no line is lost after a timeout; the instrument delays the next write by itself). No constant had to change.

**Default transport: `auto`** (it was `raw`). Every tool works over VXI-11 with the same values, VXI-11 is better where they differ (commands queued during a sweep instead of dropped, no hold-off after an unsupported query, an exact blocking sweep wait, the full screenshot), and `auto` still falls back to raw when the portmapper or the VXI-11 link is not available. Remaining reasons to use `UTS_TRANSPORT=raw`: a firewall that blocks the dynamic VXI-11 port (the fallback covers a blocked port 111 or a failing `create_link`), a tunnel on the raw port (giving a port without a transport already selects raw), and other analyzer models that were not tested.

## Network discovery (issue #85; firmware V1.04.0040)

- The analyzer answers a **UDP portmapper `GETPORT` (program 395183 v1, TCP)** sent to its address on port 111 with the dynamic VXI-11 core port, within a few milliseconds; `*IDN?` over that VXI-11 port and a plain TCP connect to 5025 both work, and discovery sent nothing else (the error queue stayed clean, no setting touched).
- The broadcast form (directed broadcast to the subnet) was **not** verifiable on the bench: the analyzer sits on a different (routed) subnet than the computer, and directed broadcasts do not cross routers. This is the intended limit: discovery never goes beyond the local subnets. A unicast request to the analyzer's address (the same code path with an explicit target) found it and identified it (UTS3036B, V1.04.0040).
